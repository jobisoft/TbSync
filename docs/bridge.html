The bridge

Repo: TbSync, beta builds only. beta/modules/bridge.mjs plus a native messaging helper.

Exposes TbSync's internal manager RPC table on a loopback HTTP socket, so a script can drive it from a shell — import a fixture, sync, read the wire log back, assert — without a rebuild-install-paste cycle per step.

shell --HTTP--> native host --native messaging--> bridge --> RPC table

The bridge is only shipped in the beta xpis.

Verbs

COMMANDS is the entire surface, and is both the allow-list and the scope declaration so the two cannot drift. Account lifecycle — add, delete, edit, authenticate — is not supported. That is why several test-plan sections need a human.

Scope is what a verb may touch. account and folder verbs check the ids passed against the chosen target and refuse otherwise; calendar and book verbs take no resource id at all — the target's is supplied, so there is no argument left to get wrong. Those two also require the granted folder to still be of that kind, so a book verb against a calendar folder is refused with the mismatch named, rather than reaching the platform as an id the caller never chose. Unscoped verbs read configuration or turn a global knob. A bridge with nothing chosen answers "no" rather than "anything".

The Bridge tab grants one resource per kind — contacts, events, tasks — each select offering only folders of that kind, filtered on the host's own targetType. So a contacts test and a calendar test no longer take turns over a single grant. A calendar verb acts on the events grant by default; pass resource: "tasks" to aim it at the tasks one. That argument chooses between your grants and can never name a resource that was not granted.

VerbScopeDoes
getState— Providers and their connection state, accounts and their status. How a caller discovers what the target could be.
getBrowserInfo— Name, version and buildID of the running Thunderbird. Beats inferring it from the process list.
getFolders— The account's folder rows: selection, status, target id, sync key, changelog, and the provider's custom data.
setLogLevel— Event Log verbosity. debug entries are dropped below level 3.
getEventLog— Log entries, optionally only those newer than sinceSeq. Entries carry a per-process sequence number, so "what did this sync produce" is exact rather than guessed from timestamps. Reports dropped when the buffer rolled past what the caller last saw.
clearEventLog— Empty it, so the next step starts from a known point.
getConsole— Thunderbird's own console, which the Event Log never sees — a TypeError inside a calendar module, an iCal parse complaint, a script that failed to load. Same sinceSeq shape, and seeded from the platform's backlog on first use.
clearConsole— Drop what is held.
syncAccountaccount Sync, and wait for it to finish — unlike the manager's RPC of the same name, which does not await. Returns the folder rows, which is how you tell "synced cleanly" from "did nothing at all": it returns early and silently for an account that is disabled, already syncing, holding E:AUTH, or whose provider is not connected.
setAutoSyncIntervalaccount Set the account's autosync interval.
setFolderSelectedfolder Select or deselect a folder. Deselecting drops the target and resets the folder's sync key, which is how a run starts from a known state.
reloadHost— Reload TbSync itself. Answers before reloading, and has to: the reload takes the native port with it, the helper dies with the port, and the response in flight dies with the helper. Expect the endpoint to disappear and come back — poll /health rather than assuming the next request lands.
storage.snapshot— All of storage.local. Save it to a file before storage.clear — it is the only way back, and it contains the account credentials and OAuth refresh token.
storage.clear— Empty the add-on's persistent state, so the next reload behaves like a fresh install — the only way to exercise the legacy importer, which runs only when tbsync.accounts is absent. Returns what it removed. The bridge's own enabled flag and target are kept, or the reload would come back with the port closed and no way to restore.
storage.restore— Write a snapshot back. The bridge's own two keys are skipped: restoring them verbatim would let a script grant itself a different target, and clear never removes them anyway.
reloadProvideraccount Ask the account's provider to reload itself. Fails if that provider is not connected.
calendars.synchronizecalendar Refresh the target calendar, as the Reload button does. For a provider-backed calendar it is the only way to reach calendar.provider.onSync from a script — the same entry point the button and the platform's refresh timer use.
calendars.renamecalendar Rename the target calendar. The provider that supplies it mirrors the new name into its folder row, so this is how that path is driven from a script.
calendars.removecalendar Delete the target calendar, as the Remove button does — the API's remove unregisters it, which ends in deletePrefBranch. The folder row is left pointing at it, and the provider is expected to notice and clear the binding.
items.querycalendar Items in the target calendar, as iCal. Any other query option is passed through.
items.getcalendar One item by id, as iCal.
items.createcalendar Create from an iCal string. type defaults to event; an id may be pre-specified, which is how a fixture keeps the UID it was written with.
items.updatecalendar Replace an item's iCal.
items.removecalendar Delete an item by id.
contacts.querybook Cards in the target book. Each carries its vCard in properties.
contacts.getbook One card by id.
contacts.createbook Create from a vCard string. An id may be pre-specified, so the changelog entry the create produces can be asserted on rather than hunted for.
contacts.updatebook Replace a card's vCard. Writing back a byte-identical one should produce no changelog entry — that is the ghost gate, which exists because Thunderbird also fires onUpdated for PopularityIndex and address-picker recency.
contacts.removebook Delete a card by id.
lists.querybook Mailing lists in the target book.
lists.getbook One list by id.
lists.createbook Create from name, and optionally nickName and description. A list has no vCard representation, so it is properties rather than a payload.
lists.updatebook Change those properties. Renaming one drives the list-by-name pre-tag, where a pulled list is tagged by name and upgraded to a real id on the next onCreated.
lists.removebook Delete a list by id.
lists.addMemberbook Put an existing card in a list.
lists.removeMemberbook Take it out again.
lists.listMembersbook The cards in a list.
Never reload mid-sync. SYNC_FOLDER has no timeout and nothing rejects it when the port drops, so the helper dies, the response never arrives, and recovery needs about:debugging. Let syncAccount return first.

Deselect the test resource before executing a reload. Nothing can then be in flight, and the next run starts from a reset sync key instead of whatever the last one left behind.

Running it

Build the beta xpis with npm run build in each repo and install them as temporary installs from about:debugging, which is what makes reloadHost and reloadProvider work.

After installing the temporary XPIs, enable the bridge in the TbSync Manager interface.
