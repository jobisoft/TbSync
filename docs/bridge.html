The bridge

A development aid, in beta builds only. It exposes TbSync's internal RPC table on a loopback HTTP socket, so a script can import a fixture, sync, read the wire log back and assert — without a rebuild-install-click cycle per step. Both providers' test suites are driven through it.

shell --HTTP--> native helper --native messaging--> bridge --> RPC table

Targets and scope

The Bridge tab grants one resource per kind — contacts, events, tasks — each select offering only folders of that kind. Every verb declares what it may touch, and the declaration is also the allow-list, so the two cannot drift:

  • account and folder verbs check the ids they are passed against the grant and refuse otherwise;
  • calendar and book verbs take no resource id at all — the grant supplies it, so there is no argument left to get wrong. They also require the granted folder to still be of that kind. A calendar verb uses the events grant by default; pass resource: "tasks" to aim it at the tasks one;
  • unscoped verbs read configuration or turn a global knob.

A bridge with nothing chosen answers "no" rather than "anything". Account lifecycle — add, edit, authenticate — is deliberately absent, which is why parts of the manual test plan still need a person.

Unrestricted mode is not a convenience flag. With it on, a script may self-grant any account and reach every resource — including connecting accounts and enabling resources that are not synced yet, which pulls them down. The target stops being a boundary and becomes a current state. That is the point for unattended multi-account runs, and exactly why it is opt-in, toggleable only from the Bridge tab, and meant to be switched off afterwards. Credentials are not part of what it adds: Thunderbird's password store is never reachable through the bridge.

Two rules

Never reload mid-sync. SYNC_FOLDER has no timeout and nothing rejects it when the port drops, so the helper dies, the response never arrives, and recovery needs about:debugging. Let syncAccount return first.

Deselect the test resource before a reload. Nothing can then be in flight, and the next run starts from a reset sync key instead of whatever the last one left behind.

Running it

Build the beta xpis with npm run build in each repo and install them from about:debugging as temporary add-ons — that is what makes reloadHost and reloadProvider work. Then enable the bridge in the TbSync Manager's Bridge tab and pick a target.
