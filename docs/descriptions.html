How things work

The host and its provider contract. Anything specific to a provider lives in that provider's own notes — for Exchange ActiveSync, EAS-4-TbSync.

Provider discovery

Repo: TbSync, with the matching provider half vendored into EAS-4-TbSync and google-4-tbsync. The first three panels show the protocol 1.3 handshake under every startup order; the last two show what happens when only one side of it is installed, which is what users see mid-rollout.

Why no race remains

Two rules, one on each side:

  1. each side attaches its listener before it sends anything;
  2. each side sends exactly once when it is ready — the host a fire-and-forget DISCOVERY.HOST_READY, the provider its ANNOUNCE.

That is enough. Whichever background page starts later sends into a listener that is already attached, because the earlier one attached its listener before it sent. So at least one of the two messages always lands:

  • host starts later → its host-ready reaches the provider → provider re-announces;
  • provider starts later → its announce reaches the host directly.

There is no third case. The two messages cannot both be lost, because losing the announce means the host had not started, and losing the host-ready means the provider had not started — and they cannot both have not-started at the moment the other one sent.

The host-ready message carries nothing and establishes nothing. It is a nudge: the real handshake is still ANNOUNCE → providers.upsert → openPortToProvider, unchanged.

Testing it

Enable order alone covers every case; nothing needs to be instrumented:

  • enable the provider, wait 10 s, enable TbSync → exercises the host-ready path;
  • enable TbSync, wait 10 s, enable the provider → exercises the announce path;
  • restart Thunderbird → exercises both starting together.

Each must end with an account actually syncing, not merely with the provider listed.

Who notices a user's edit

Calendars: the provider. Contacts: the host. Not a compromise - the platform is asymmetric and the split follows it.

A provider can supply its own calendar type, and Thunderbird then hands it every user edit directly, with the previous item attached, while the provider's own writes go somewhere the hooks do not see. So the provider knows which edits are the user's without anything having to be marked, and it can say what changed rather than only that the item did. It reports them with CHANGELOG_RECORD_USER_EDIT, into the same folder.changelog the push already reads: the host still owns that table, only the author of an entry changed.

Address books have no equivalent. addressBooks.provider offers one event, onSearchRequest, and nothing for items. So the host keeps observing them, and keeps pre-tagging its own writes so its observer can tell them from the user's. That logic - the ghost gate for Thunderbird's usage-tracking updates, the contact hashes, the list-by-name pre-tag - is better in one place than vendored into every provider.

Consequences worth knowing:

  • The host runs no calendar listener at all, and has no calendar API in the shipped build. Rename mirroring and deselecting a folder whose calendar the user deleted are the provider's work, reported with FOLDER_TARGET_REMOVED.
  • *_by_server pre-tags are never written for a provider-owned target. Nothing would consume them, and they would accumulate one per synced item.
  • The rule is the folder's targetType, so it holds only while every provider that syncs calendars supplies its own type.

Anything that reaches the server needs its own E:AUTH guard

Repo: every provider. The host cannot add these guards for you.

When the host stamps error: "E:AUTH", the server has rejected the account's credentials. Every provider path that reaches the network must decline to run until that clears — not just the sync path. Presenting rejected credentials repeatedly is how a server decides to lock an account out, and one unguarded entry point is enough.

An E:AUTH account stays enabled: it keeps folders, sync keys, calendars and address books, and is only held back from syncing. What the host guards is the sync path, at one choke point in sync-coordinator.mjs::syncAccount:

if (!acc || !acc.enabled) return;
if (acc.error === ERR.AUTH) return;

That covers all five callers of syncAccount and nothing else. A provider entry point the host does not invoke is invisible to it, and enabled is not a proxy for "safe to talk to the server".

The one live example is onSearchRequest in EAS's gal.mjs, backing the per-account GAL address book. It fires on every keystroke in a compose window, outside the sync path, and issues an authenticated EAS Search. Two things about its guard are deliberate: it sits inside the callback, not around the registration, because deregistering would stop the traffic with nothing to put it back — an auth failure raises no account-enabled event; and it tests === ERR.AUTH rather than "any error", because a folder-level failure should still answer autocomplete.

When adding an entry point, ask: can this reach the server without the host having called me? If yes it needs the guard — anything on addressBooks.provider.*, calendar.provider.*, a runtime message from your own UI pages that performs network work, or a timer, alarm or observer you install yourself. account.error is on the row getAccount returns.
