How things work

The parts of the host a provider author has to know about. Anything specific to one protocol lives in that provider's own notes — for Exchange ActiveSync, EAS-4-TbSync.

Finding each other

Host and provider are separate add-ons with separate background pages, and either can start first. Two rules make that safe, and there is nothing else to it:

  • each side attaches its listener before it sends anything;
  • each side sends exactly once, when it is ready — the host a fire-and-forget DISCOVERY.HOST_READY, the provider its ANNOUNCE.

Whichever page starts later sends into a listener that is already there. If the host starts later, its host-ready reaches the provider and the provider announces; if the provider starts later, its announce reaches the host directly. Both messages cannot be lost, because losing the announce means the host was not running and losing the host-ready means the provider was not — and they cannot both have been not-running when the other sent.

Host-ready carries nothing and establishes nothing; it is a nudge. The handshake is ANNOUNCE → providers.upsert → openPortToProvider.

To test it, enable order is enough: enable the provider, wait, enable TbSync (exercises host-ready); enable TbSync, wait, enable the provider (exercises announce); restart Thunderbird (both together). Each must end with an account actually syncing, not merely with the provider listed.

Who owns a change queue

Before a local edit can be pushed, something has to notice it. Which side notices depends on what Thunderbird offers, and the split follows the platform rather than a preference.

Calendars and task lists: the provider. A provider can register its own calendar type, and Thunderbird then hands it every user edit directly, with the previous item attached, while the provider's own sync writes go to <id>#cache, which fires no hooks. So the provider can tell a user edit from its own write structurally, and can say what changed rather than only that something did. It keeps those edits in its own storage: the hook answers while Thunderbird holds the user's save, so the record must not depend on the host being alive.

Address books: the host. There is no equivalent API — addressBooks.provider offers only onSearchRequest — so the host observes book events itself and keeps those entries in folder.changelog. It pre-tags its own writes (*_by_server) so its observer can tell them from the user's. That machinery — the ghost gate for Thunderbird's usage-tracking updates, the contact hashes, the list-by-name pre-tag — is better in one place than vendored into every provider.

Consequences worth knowing:

  • The host runs no calendar listener and ships no calendar API. Mirroring a rename, and clearing the binding when the user deletes a calendar, are the provider's work — reported with FOLDER_TARGET_REMOVED.
  • folder.changelog stays empty for a provider-owned folder. HOST_CMD.GET_CHANGELOG is how anything reads those queues.
  • The needs-sync badge is driven by folder.custom.pendingUserChanges, which the provider keeps roughly current. It is best-effort by design: a stale count shows or hides a dot, and nothing reads it to decide what to sync.
  • The rule is the folder's targetType, so it holds only while every provider that syncs calendars supplies its own type.

Sessions

A folder row outlives the things hanging off it. It is deselected and selected again; its calendar is deleted and re-created by the next sync. Each time, the sync state that belonged to the old binding — keys, id maps, pending edits — is worthless, and pushing those edits into the new binding would re-apply them to a resource the user never touched.

The host cannot delete that state itself: most of it lives in the provider, and Disconnect and Remove have to work when the provider is broken or uninstalled — that is what makes them recovery paths. So the host does not delete; it renames. Every folder row carries a sessionId, minted by the host and never reused, and ending a binding means minting a new one.

A provider therefore MUST:

  • read sessionId from the folder row, never cache it across a sync;
  • key everything it persists per folder by it;
  • drop, on sight, anything stored under a session no folder row names.

Teardown is then one local host write that needs nobody's cooperation. A provider that was not running misses nothing: it finds out by not finding its session.

The E:AUTH rule

Every provider path that reaches the network needs its own guard. The host cannot add them for you.

When the host stamps error: "E:AUTH", the server has rejected the account's credentials. Presenting rejected credentials repeatedly is how a server decides to lock an account out, and one unguarded entry point is enough to keep doing it.

An E:AUTH account stays enabled: it keeps its folders, sync keys, calendars and address books, and is only held back from syncing. What the host guards is the sync path, at one choke point in sync-coordinator.mjs::syncAccount:

if (!acc || !acc.enabled) return;
if (acc.error === ERR.AUTH) return;

That covers the five callers of syncAccount and nothing else. An entry point the host does not invoke is invisible to it, and enabled is not a proxy for "safe to talk to the server".

The live example is onSearchRequest in EAS's gal.mjs, backing the per-account GAL address book: it fires on every keystroke in a compose window, outside the sync path, and issues an authenticated EAS Search. Two things about its guard are deliberate. It sits inside the callback rather than around the registration, because deregistering would stop the traffic with nothing to put it back — an auth failure raises no account-enabled event. And it tests === ERR.AUTH rather than "any error", so a folder-level failure still answers autocomplete.

When adding an entry point, ask: can this reach the server without the host having called me? If yes it needs the guard. That covers anything on addressBooks.provider.* or calendar.provider.*, a runtime message from your own UI pages that performs network work, and any timer, alarm or observer you install yourself. account.error is on the row getAccount returns.
