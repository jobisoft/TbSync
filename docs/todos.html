Features and gaps

CANCEL_SYNC has no sender

Repo: TbSync. Priority low — a longstanding gap, not a regression. The command is declared in protocol.mjs and dispatched by the provider base class; both providers answer it with return null. The host never sends it, so there is no way to cancel a running sync.

It matters because a sync in progress locks the account out of the UI entirely — transientLocked = upgrading || syncing || busy gates Remove along with everything else — and SYNC_ACCOUNT / SYNC_FOLDER are in NO_TIMEOUT_CMDS. A provider that is alive but not returning leaves the account reading "Synchronizing…" with every action greyed out, recoverable only by restarting Thunderbird.

Cancellation was designed for: #onPortMessage dispatches without await, so a cancel sent while a SYNC_FOLDER is outstanding would reach the provider immediately rather than queueing behind it. It was never wired up. Who should be able to cancel: the user, from the manager, and nobody else — a provider that dies mid-sync already causes the outstanding RPC to reject.

Layer 1 — host-side stop, no protocol involvement. A cancelledAccounts set in transient.mjs; syncAccount checks it in the per-folder loop and in the do/while rerun loop and breaks; a cancelSync manager RPC sets it; the manager's Sync button becomes Stop while syncing. The existing finally already downgrades pending folders to "aborted". This stops at the next folder boundary rather than interrupting the folder in flight — a feature, since the provider is never left mid-write.

Layer 2 — give the command a real implementation. The host sends it; EAS holds a per-account AbortController and aborts the request in flight. fetchWithTimeout already threads a signal, so it would combine its own timeout with an external one (AbortSignal.any).

Layer 1 first. Layer 2 alone would be worse than either — it would abort the current request while the loop marched on to the next folder.

A provider that dies mid-sync locks the account

Repo: TbSync. SYNC_ACCOUNT and SYNC_FOLDER are in NO_TIMEOUT_CMDS deliberately, but if the provider stops answering nothing rejects the pending RPC: syncingAccounts keeps the account, the manager shows a permanent spinner, and no further sync can start. reloadProvider does not clear it; only reloadHost does, because syncingAccounts is module state a reload discards.

The port dropping should be enough to fail the in-flight command. router.handleDisconnect exists; whether it rejects pending entries, and whether the provider's #rejectAllPending covers the reverse direction, is where to start. An unrecoverable lock turns any provider bug into "restart Thunderbird".
