Features and gaps

CANCEL_SYNC — done

Repo: TbSync. Shipped: the host sends it, and the provider base class implements it, so both providers inherit a working cancel.

What was built differs from the plan that stood here. There is no Stop button: Disconnect is the cancel, and it is gated on nothing but the account being connected — not on the provider being alive, not on a sync, an upgrade or a busy RPC — because every one of those is a state where the user needs it most. abortAccountSync marks the account in cancellingAccounts, sends CANCEL_SYNC without awaiting it (waiting would mean waiting out the RPC timeout in exactly the case this exists for), and then rejects the account's in-flight commands with E:CANCELLED — which is what actually ends a sync parked on a NO_TIMEOUT_CMDS command. Both layers landed together: the loop checks alone would have left the request in flight, and the abort alone would have let the loop march on to the next folder.

Disconnect requires the provider's port to be up. Only the provider can tear down the Thunderbird resources it owns — the host has no calendar API — and a disconnect without it strands calendars with refresh timers still armed, while the provider's own account state (its FolderSync key) never learns the teardown happened. A dead provider leaves one exit, Remove, which works ungated and knowingly leaves the targets behind until the provider reappears or the user deletes them by hand.

Still open: a cancel is only as good as the provider's willingness to stop — a third-party provider that ignores the verb gets its commands settled anyway and may keep writing into targets the teardown has removed. An ACCOUNT_DISABLED that times out on a connected-but-unresponsive provider currently proceeds with a warning, teardown possibly incomplete; whether it should instead leave the account connected is undecided. And orphaned targets left by remove-while-dead are considered fixable, later.

A provider that dies mid-sync locks the account

Repo: TbSync. SYNC_ACCOUNT and SYNC_FOLDER are in NO_TIMEOUT_CMDS deliberately, but if the provider stops answering nothing rejects the pending RPC: syncingAccounts keeps the account, the manager shows a permanent spinner, and no further sync can start. reloadProvider does not clear it; only reloadHost does, because syncingAccounts is module state a reload discards.

The port dropping should be enough to fail the in-flight command. router.handleDisconnect exists; whether it rejects pending entries, and whether the provider's #rejectAllPending covers the reverse direction, is where to start. An unrecoverable lock turns any provider bug into "restart Thunderbird".
