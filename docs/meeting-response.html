MeetingResponse — answering invitations over EAS

Repo: EAS-4-TbSync. Contributed feature, deferred. State as of 30 Jul 2026.

The concept

EAS carries an attendee's answer to an invitation in its own command, MeetingResponse, with UserResponse 1 = Accept, 2 = Tentative, 3 = Decline, optionally scoped to one occurrence of a series by InstanceId. The server replies Status 1 and applies the answer to the organizer's tracking and the attendee's copy.

Today an answer travels a different route. Thunderbird's itip engine sets the local PARTSTAT, and the sync pushes that as an ordinary <Add> or <Change>. Exchange reads it as a client creating a self-organized meeting: it makes a second event owned by the person who answered and invites every attendee again (#320; #8, #10, #66 describe the same thing).

In v4, attendee status is inbound only — read from ResponseType and AttendeeStatus, never sent.

Waiting for the server to apply the answer

Status 1 acknowledges receipt; Exchange updates the calendar item afterwards. The panels show that gap and the proposed handling.

Tomas measured the post-response fan-out at ~30 s under load. The 34 s is what the re-poll schedule budgets for itself — 2+4+8+10+10 from settleWaitMs(n) = min(POST_PUSH_WAIT_MS · 2n-1, 10000) over five pulls — with each iteration adding a full pullPhase on top. The measurement is bracketed by the polls that produced it: absent at 24 s, present at 34 s.

A Ping-based listener

EAS has a change-notification channel. The client issues Ping (codepage 13) with a HeartbeatInterval and the Folder ids to watch; the server holds the request open until one of those collections changes or the heartbeat expires, then answers. Supported in every protocol version from 2.5 to 16.1, and the vocabulary is already in wbxml-codepages.mjs.

It behaves as a listener but is built as a loop: the client reissues the request after every response. HeartbeatInterval is cached server-side after the first request, so later ones need only the folder list. Per MS-ASCMD Status (Ping):

  • 2 — something changed; the response names the folders. Sync each, then reissue.
  • 1 — heartbeat expired, nothing changed. Reissue.
  • 5 — heartbeat outside the allowed range; the response carries the nearest allowed value to use.
  • 6 — too many folders; the response carries MaxFolders.
  • 7 — folder hierarchy is stale; FolderSync, then reissue.
  • 3, 4, 8 — missing parameters, malformed WBXML, transient server error.

Applied here, the server's post-response update announces itself: no delay constant, no repeated polling, no sync held open. The same channel covers every incoming change rather than this one case.

A listener fits this better than waiting on a fixed schedule, whatever the constants are set to. A schedule has to guess how long a server will take, and holds the sync open for the length of the guess - which is what locks the account, since a running sync greys out Sync, Remove and Disconnect with no way to cancel (cancel-sync.md). Changing the numbers moves the cost between a missed update and a longer lock rather than removing either. The server already knows when it is done, and Ping is how it says so.

What it needs: one held request per account, kept alive across sleep/wake and connection drops; a timeout policy of its own, since the default request timeout is 90 s and a useful heartbeat is longer; and the folder list kept in step with what the user has selected.

Open items

  • Stale-marker guard. The first commit maps ATTENDEESTATUS_TO_PARTSTAT[5] to NEEDS-ACTION. On calendars written by an earlier build, compareSelfPartstat reads a stored ACCEPTED against X-EAS-RESPONSETYPE=5, treats it as a transition, and sends an Accept for an invitation the user never answered — on any local write, including a dismissed reminder. Niel flagged it; Tomas confirmed it and that his test items were all freshly synced. Merge condition.
  • The waiting mechanism needs replacing, not tuning. The re-poll commit on Tomas Kovacik's branch polls on a fixed schedule with the sync held open. Ping is the direction we would rather take. The diagnosis behind it stands - the server really does apply the answer later, and that is worth acting on - but through a listener. If any of that branch is taken as-is in the meantime, its step 4 condition also has to be reconciled with the postPushSettle gate: if ((pushed.changedAnything && ctx.postPushSettle) || ctx.pendingResponseServerIds.size).
